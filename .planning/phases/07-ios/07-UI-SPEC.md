# Phase 7 — UI Design Contract

> Visual and interaction contract for the iOS·텔레그램 네이티브 폴리시 phase. Generated by gsd-ui-researcher, verified by gsd-ui-checker.
>
> **Scope note (read first):** This is a **native-polish phase, NOT a redesign.** The design system is LOCKED upstream in `.planning/phases/01-db/01-UI-SPEC.md` (Tailwind v4 `@theme` tokens, coral identity, BM/Pretendard fonts, emoji whitelist). This contract does **not** re-derive spacing/typography/color from scratch — it **inherits** Phase 1 and specifies ONLY the genuinely new visual/interaction surfaces this phase introduces or changes:
> 1. **Loading skeletons** (NEW visual — the one real UI deliverable, NATIVE-05).
> 2. **`--safe-b` safe-area spacing token** (NATIVE-01) — a spacing-token contract replacing hardcoded `env()` in 8 bottom-fixed surfaces.
> 3. **Native Telegram MainButton params contract + DOM fallback** (NATIVE-04) and the FAB action wiring (NATIVE-02). The pixels of the native MainButton are rendered by the Telegram client, not by us.
>
> Most of this phase is **invisible behavior** (haptics, SDK lifecycle, BackButton wiring) — those carry no new visual contract and are governed by 07-RESEARCH.md, not here.

## Spacing Scale

Inherited from Phase 1 (4px base scale, fixed-chrome exceptions). **Unchanged.** This phase adds **one new spacing token** and one keyframe; everything else is referenced, not redefined.

### New token (NATIVE-01 / D-02) — `--safe-b`

The single source of bottom safe-area inset. Replaces the hardcoded `env(safe-area-inset-bottom)` in all 8 bottom-fixed surfaces.

| Token | Definition | Where defined |
|-------|------------|---------------|
| `--safe-b` | `max(var(--tg-viewport-content-safe-area-inset-bottom, 0px), env(safe-area-inset-bottom, 0px))` | `app/globals.css` `:root` |

- Primary source is the SDK-bound `--tg-viewport-content-safe-area-inset-bottom` (already bound by `viewport.bindCssVars()` in `lib/telegram.ts` boot — do NOT re-bind, throws `CSSVarsBoundError`). `content`-safe-area is correct for in-app bottom UI (excludes Telegram's own chrome).
- `env(safe-area-inset-bottom, 0px)` is the fallback for non-Telegram browsers. iOS Telegram WebView returns this as `0` — that is the bug this token fixes.
- **Consumption pattern:** every bottom-fixed surface that previously wrote `calc(Xpx + env(safe-area-inset-bottom))` becomes `calc(Xpx + var(--safe-b))`. The constant `Xpx` per call-site is **preserved exactly** (no visual padding change beyond the inset correction).

**The 8 call-sites that must switch from `env()` to `var(--safe-b)` (visual padding constants kept identical):**

| File | Current | Becomes |
|------|---------|---------|
| `components/BottomNav.tsx` (L49) | `8px 8px calc(22px + env(safe-area-inset-bottom))` | `8px 8px calc(22px + var(--safe-b))` |
| `components/TgMainButton.tsx` (L34) | `10px 14px calc(14px + env(safe-area-inset-bottom))` | `10px 14px calc(14px + var(--safe-b))` |
| `app/(mini)/order/[id]/page.tsx` (L164) | `10px 14px calc(14px + env(safe-area-inset-bottom))` | `10px 14px calc(14px + var(--safe-b))` |
| `app/(mini)/_components/ShareEntryButton.tsx` (L118) | `bottom: calc(90px + env(safe-area-inset-bottom))` | `bottom: calc(90px + var(--safe-b))` |
| `app/(mini)/feed/_components/ReportMenu.tsx` (L109) | `20px 18px calc(20px + env(safe-area-inset-bottom))` | `20px 18px calc(20px + var(--safe-b))` |
| `app/(mini)/feed/_components/ReportMenu.tsx` (L177) | `bottom: calc(90px + env(safe-area-inset-bottom))` | `bottom: calc(90px + var(--safe-b))` |
| `app/share/[id]/_components/ShareSheet.tsx` (L209) | `bottom: calc(28px + env(safe-area-inset-bottom))` | `bottom: calc(28px + var(--safe-b))` |

> Note: `app/layout.tsx` uses `env(safe-area-inset-**top**)` for the status-bar — that is a **top** inset and is OUT of scope for `--safe-b` (which is bottom-only). Leave the top inset as-is. `app/(mini)/layout.tsx` comment references env safe-area but the active bottom inset lives in BottomNav — confirm during impl whether the layout itself sets a bottom padding (if so, switch it too; if it only documents, leave the comment).

## Color

Inherited verbatim from Phase 1 (60/30/10 coral split, full locked token set). **No new color.** Two color-relevant constraints this phase introduces:

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `#FFF7F1` (`--color-bg`) | Skeleton screen background (matches the shell it replaces) |
| Secondary (30%) | `#FFFFFF` (`--color-surface`) | Unchanged |
| Accent (10%) | `#FF5A33` (`--color-primary`) | See reserved list below + native MainButton `backgroundColor` |
| Skeleton fill | `#FFE9E1` (`--color-primary-soft`) | Pulse blocks ONLY (see § Loading Skeleton Contract) |
| Destructive | none new | No destructive flow added this phase (FAB → `/home` is non-destructive). CancelModal "그만 참을래요" keeps its existing Phase-3 custom color `#8a5a3a` and stays DOM (D-08). |

**Accent (`--color-primary` #FF5A33) reserved-for list — Phase-7 additions only** (full list lives in Phase 1):
- **Native Telegram MainButton `backgroundColor`** = `#FF5A33` with white `textColor` — matches the DOM `TgMainButton` coral fill so the native and fallback buttons are visually consistent. (Note: D-08 flags that custom MainButton color is a native limitation — set it on a best-effort basis; if the client ignores it, the native default applies. Color-critical / sub-line CTAs stay DOM.)
- **Skeleton pulse blocks** use `--color-primary-soft` (#FFE9E1), the soft coral tint — brand-consistent, low-contrast, never the full `--color-primary` (a full-coral skeleton would read as content, not a placeholder).

Skeleton color rule (Dim 3 guardrail): pulse blocks are `--color-primary-soft` on the `--color-bg` cream surface. Do NOT introduce greys, do NOT use full `--color-primary`, do NOT add a new skeleton-grey token.

## Loading Skeleton Contract (NATIVE-05 — the primary new visual)

**ONE reusable skeleton primitive, parametrized per screen.** Do NOT design 7 bespoke skeletons. Each `loading.tsx` is a pure server file (no SDK, no client JS, no data, no params) that renders instantly as the route segment's Suspense fallback while the async RSC resolves.

### Skeleton block primitive (shared visual language)

| Property | Value |
|----------|-------|
| Fill | `var(--color-primary-soft)` (#FFE9E1) |
| Animation | `pulse 1.2s ease-in-out infinite` (new keyframe above) |
| Radius | match the real element it stands in for: cards **18px** (`--radius` Card), tiles **14–16px**, pills **999px**, header band squared/12px (per the shell) |
| Container padding | match the real screen's horizontal padding (**16px** default) |
| Background | inherit `--color-bg` (cream) — the skeleton sits on the same surface as the loaded screen |

**Skeleton must mirror the shell layout** of its target screen (same header height, same card/list/tile placeholder positions) so the swap to real content is positionally stable ("끊김" removal). It is a **shape echo**, not a detailed mock.

### Per-segment skeleton spec (7 files, D-10)

| Segment (`loading.tsx`) | Target screen | Skeleton shape echo |
|-------------------------|---------------|---------------------|
| `app/(mini)/feed/loading.tsx` | 명예의 전당 피드 | 4× full-width feed-card blocks (~120px tall, radius 18, 12px gap), under the standard 16px padding |
| `app/(mini)/stats/loading.tsx` | 통계 대시보드 | 1× hero block (dark-card footprint, ~96px) + 3× stat-tile blocks in a row + 1× wide weekly-chart block |
| `app/(mini)/my/loading.tsx` | MY | profile-header block (avatar circle + 2 text bars) + cumulative-summary block + 2–3 record-card blocks |
| `app/(mini)/store/[id]/loading.tsx` | 가게 상세 | store-hero block + 3–4 menu-row blocks |
| `app/(mini)/post/[id]/loading.tsx` | 인증 작성 | receipt block + 2× dual-photo square blocks (side by side) + caption-field block |
| `app/(mini)/order/[id]/loading.tsx` | 주문 확정 | receipt-summary block + bottom CTA-height block above `--safe-b` |
| `app/(mini)/wait/[id]/loading.tsx` | 배달 대기 | stepper-row block + map block (large) + gauge block |

- Skeleton blocks reuse the **locked radii/spacing tokens** — no new measurements invented per screen; the shape echo uses the same card/tile radii and 16px padding the loaded screen uses.
- **No text, no copy, no emoji** in skeletons. They are pure shape. (Avoids the Pitfall-Phase-1 entrance-fade-stuck-at-opacity-0 risk: pulse oscillates `.55–1`, never resting at 0.)
- If a target segment turns out to be fully static (resolves instantly), its skeleton is a harmless no-op (RESEARCH Pitfall 4) — acceptable; document it rather than removing.

## Native MainButton Params Contract (NATIVE-04 / D-07, D-08)

The native button's **pixels are Telegram's**, not ours. This contract governs the **parameters** we set and the **progressive-enhancement fallback**.

### Params we set (via `setMainButtonParams`, per `useNativeMainButton` hook)

| Param | Value | Notes |
|-------|-------|-------|
| `text` | the existing per-CTA label (unchanged copy — see Copywriting) | label-only CTAs only |
| `backgroundColor` | `#FF5A33` (`--color-primary`) | best-effort; matches DOM fallback. May be ignored by client (D-08 native-color limit) |
| `textColor` | `#FFFFFF` | white, matches DOM `TgMainButton` |
| `isVisible` | `true` on the owning route, **`false` on cleanup** | ghost-button prevention (RESEARCH Pitfall 1) |
| `isEnabled` | `!disabled` | mirrors DOM disabled state |
| `isLoaderVisible` | `loading` | native loader = DOM `TgMainButton` busy/disabled-press state |

### Progressive enhancement contract (D-07/08)

- **Native-supported platform:** native MainButton is shown (`setMainButtonParams.isAvailable()` true), and the in-DOM `TgMainButton` for that CTA is **hidden/suppressed** so there is no double CTA. (Impl detail per call-site; the contract is "exactly one primary CTA visible.")
- **Non-supporting platform / outside Telegram:** hook no-ops (guarded by `.isAvailable()`); the **DOM `TgMainButton` stays as the pixel-identical fallback** with all Phase-1 visuals intact (coral fill, white 17/800 label, min-height 54, `--safe-b` bottom padding, press scale .98, disabled `#E3D8CE`).
- **Stay-DOM CTAs (D-08 — native NOT used):** any CTA needing a **sub-line** or a **custom color**:
  - CancelModal "그만 참을래요" (custom `#8a5a3a`) → DOM + add `haptic.impact('medium')` on press.
  - Any `TgMainButton` with a `sub` prop → DOM + haptic.
  - These keep their full Phase-1 DOM visual; only haptic is added.

Candidate native-ization sites (planner picks label-only ones; per RESEARCH Open Q2): WelcomeIntro "시작하기", cart/order primary CTAs, store/post primary CTAs. Color/sub-line ones stay DOM.

### Center "참기" FAB (NATIVE-02 / D-04) — visual UNCHANGED

- The FAB visual is **locked from Phase 1**: 58×58 coral circle, 4px `--color-surface` border, `top:-26` offset, white ✋ (U+270B, 20px) over "참기" label (10/800), FAB shadow `0 8px 18px -4px rgba(255,90,51,.6)`. **No pixel change.**
- This phase wires its **action only**: `onCenter` default → `haptic.impact('medium')` + `useRouter().push('/home')`. Emoji stays the whitelisted ✋ (U+270B) — **NEVER** U+1FAF7. `aria-label="참기"` (already present) retained.
